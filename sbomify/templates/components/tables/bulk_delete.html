{% comment %} The confirmation every bulk delete goes through. Nothing is deleted until a person reads what is about to go and presses the button that names it: the bulk bar's Delete only opens this dialog (confirmDelete()), and the dialog is the only thing that posts. It reads the tableSelection state on the shell, so it goes inside the shell like the bulk bar. The dialog names the count and lists the first five rows by name, then how many more, so a select-all that caught more than intended is visible before it is acted on. The delete button repeats the count ("Delete 3 components"), because a button labelled only "Delete" confirms nothing. action is the URL the selection posts to, each selected id as one name field ("ids" unless name says otherwise), with the CSRF token. Without htmx it is a plain form post and the page that answers decides where to go next. With htmx it posts in place: hx_target says what the response replaces, outerHTML unless hx_swap says otherwise (with no target nothing is swapped, for an endpoint that answers with a toast and a refresh trigger). A success empties the selection and closes the dialog, and a failure keeps both so the person can try again. The delete button disables itself once pressed, so a second press cannot post twice, and an htmx request in flight holds the dialog open until it answers. The rows are read once more as the form posts, and the dialog closes by itself if the selection changes while it is open, so it never posts a set other than the one it listed. The delete button finds its form through the dialog it sits in rather than a form="" id, so two selectable tables on one page cannot submit each other's selection. id is optional and only names the dialog; without it the dialog is labelled by aria-label. htmx turns the teleport off, for the reason in modal.html: HTMX wires hx-* on the DOM it can see, and a teleported dialog is still inside its
